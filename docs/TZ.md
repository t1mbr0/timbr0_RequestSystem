## 1. Назначение и описание проблемы

Система учёта заявок создаётся для регистрации обращений и управления их выполнением. Основными пользователями являются заявители, операторы, исполнители и администраторы. Система должна хранить сведения об обращении, его категории, текущем статусе, ответственном исполнителе и истории работы.

Без единой системы обращения поступают через личные сообщения, электронную почту и устные договорённости. Сведения распределяются между несколькими источниками, поэтому сложно определить, какие заявки уже приняты, кто отвечает за выполнение и когда должен быть получен результат. При повторном обращении заявителю приходится заново описывать проблему, а руководителю — вручную собирать сведения для контроля. Возможны потеря обращения, повторная регистрация, несогласованная смена исполнителя и закрытие заявки без подтверждения результата.

Программа решает эти проблемы за счёт единой регистрации, автоматической нумерации, поиска, назначения ответственного и фиксации истории. Заявитель получает возможность отслеживать состояние обращения, оператор — распределять работу, исполнитель — видеть назначенные задачи, а администратор — управлять пользователями и контролировать весь процесс. Таким образом, система обеспечивает прозрачность, воспроизводимость истории и разграничение ответственности.

## 2. Роли и права пользователей

| Роль | Разрешённые действия | Ограничения |
|---|---|---|
| Заявитель | Создавать заявки; просматривать свои заявки; уточнять описание до назначения; добавлять комментарии; подтверждать закрытие | Не видит чужие заявки; не назначает исполнителя; не меняет справочники |
| Оператор | Регистрировать обращения; просматривать все заявки; уточнять категорию; назначать исполнителя; переводить новую заявку в работу; комментировать | Не управляет пользователями и ролями; не удаляет закрытые заявки |
| Исполнитель | Просматривать назначенные ему заявки; добавлять комментарии и отчёт о работе; переводить заявку из «В работе» в «Выполнена» | Не меняет заявителя; не назначает других исполнителей; не закрывает заявку окончательно |
| Администратор | Имеет права оператора; управляет пользователями, ролями, категориями и статусами; просматривает историю; закрывает заявки | Действия с пользователями и справочниками фиксируются; удаление связанных записей ограничено |

## 3. Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Система должна выполнять аутентификацию пользователя и определять его роль перед предоставлением доступа к функциям. |
| FR-02 | Система должна позволять заявителю и оператору создать заявку, указав тему, описание и категорию; дата регистрации заполняется автоматически. |
| FR-03 | Система должна автоматически присваивать каждой заявке уникальный номер в формате `REQ-ГГГГ-NNNNN`. |
| FR-04 | Система должна отображать перечень заявок с учётом прав роли: заявитель видит свои, исполнитель — назначенные ему, оператор и администратор — все. |
| FR-05 | Система должна обеспечивать поиск по номеру и теме, а также фильтрацию по статусу и категории с возможностью сброса фильтров. |
| FR-06 | Система должна отображать карточку заявки: номер, тему, описание, дату, заявителя, категорию, статус, исполнителя, комментарии и историю. |
| FR-07 | Система должна позволять оператору и администратору назначить или сменить исполнителя, фиксируя автора и время изменения. |
| FR-08 | Система должна поддерживать статусы «Новая», «В работе», «Выполнена», «Закрыта» и запрещать переходы, не предусмотренные жизненным циклом. |
| FR-09 | Система должна сохранять историю изменения статуса и исполнителя без перезаписи предыдущих записей. |
| FR-10 | Система должна позволять участникам заявки добавлять комментарии с указанием автора и времени создания. |
| FR-11 | Система должна поддерживать не менее четырёх категорий и позволять администратору пополнять справочник категорий. |
| FR-12 | Система должна позволять заявителю и администратору закрыть выполненную заявку после проверки результата. |
| FR-13 | Система должна позволять администратору создавать, блокировать и разблокировать учётные записи и назначать роли. |
| FR-14 | Система должна проверять обязательные поля и показывать понятное сообщение об ошибке, не удаляя уже введённые пользователем данные. |
| FR-15 | Система должна требовать подтверждения перед удалением или иным необратимым действием и ограничивать удаление связанных записей. |

### Допустимые переходы статусов

- «Новая» → «В работе»: оператор или администратор после назначения исполнителя.
- «В работе» → «Выполнена»: назначенный исполнитель или администратор.
- «Выполнена» → «В работе»: оператор или администратор, если результат требует доработки.
- «Выполнена» → «Закрыта»: заявитель владельца заявки или администратор.
- Из статуса «Закрыта» переходы запрещены; для новой проблемы создаётся отдельная заявка.

## 6. Основные сценарии использования

### UC-01. Вход в систему

**Акторы:** все роли.  
**Предусловие:** учётная запись активна.  
**Основной поток:** пользователь вводит логин и пароль; система проверяет данные; открывает список заявок согласно роли.  
**Альтернатива:** при неверных данных показывается ошибка без указания, какое именно поле неверно.

### UC-02. Создание заявки

**Акторы:** заявитель, оператор.  
**Основной поток:** пользователь открывает форму; заполняет тему, описание и категорию; отправляет форму; система проверяет поля, присваивает номер и статус «Новая», сохраняет дату и показывает карточку.  
**Альтернатива:** при ошибке валидации введённые данные сохраняются, а проблемные поля выделяются.

### UC-03. Поиск и фильтрация

**Акторы:** все роли.  
**Основной поток:** пользователь вводит номер или часть темы, выбирает статус и категорию; система показывает только доступные ему заявки, удовлетворяющие условиям.  
**Альтернатива:** при отсутствии результатов показывается пустое состояние и действие «Сбросить фильтры».

### UC-04. Назначение исполнителя

**Акторы:** оператор, администратор.  
**Предусловие:** заявка не закрыта.  
**Основной поток:** пользователь открывает карточку, выбирает активного исполнителя и подтверждает назначение; система сохраняет изменение и запись истории.

### UC-05. Изменение статуса

**Акторы:** оператор, исполнитель, администратор.  
**Основной поток:** пользователь выбирает разрешённый статус, добавляет пояснение и подтверждает действие; система проверяет роль и переход, меняет статус и пишет историю в одной транзакции.  
**Альтернатива:** недопустимый переход отклоняется с объяснением.

### UC-06. Комментирование

**Акторы:** участник заявки, оператор, администратор.  
**Основной поток:** пользователь вводит непустой комментарий; система сохраняет автора, текст и время; комментарий появляется в хронологии карточки.

### UC-07. Проверка и закрытие

**Акторы:** заявитель, администратор.  
**Предусловие:** заявка выполнена.  
**Основной поток:** пользователь проверяет отчёт исполнителя и подтверждает закрытие; система устанавливает статус «Закрыта», дату закрытия и запись истории.  
**Альтернатива:** при неудовлетворительном результате администратор возвращает заявку в работу.

### UC-08. Администрирование справочников

**Акторы:** администратор.  
**Основной поток:** администратор создаёт или изменяет категорию; система проверяет уникальность названия и сохраняет запись. Удаление категории, связанной с заявками, запрещается.

## 7. Критерии приёмки

| ID | Проверяемый критерий | Ожидаемый результат |
|---|---|---|
| AC-01 | Роли и доступ | Для четырёх ролей доступны только перечисленные в разделе 2 функции; попытка прямого доступа к чужой заявке отклоняется. |
| AC-02 | Создание | После заполнения обязательных полей появляется заявка с уникальным номером, датой и статусом «Новая». |
| AC-03 | Валидация | Пустая тема или описание не сохраняются; сообщение указывает поле, остальные введённые данные не теряются. |
| AC-04 | Поиск | Поиск по номеру и совместная фильтрация по статусу и категории возвращают корректный набор; сброс восстанавливает список. |
| AC-05 | Назначение | После выбора исполнителя его имя отображается в карточке, а в истории появляется отдельная запись. |
| AC-06 | Жизненный цикл | Все разрешённые переходы выполняются; переход «Новая» → «Закрыта» и изменение закрытой заявки отклоняются. |
| AC-07 | История | Для каждой смены статуса хранятся прежнее и новое значения, автор и дата; записи не перезаписываются. |
| AC-08 | Комментарии | Комментарий отображается с автором и временем; пустой комментарий не сохраняется. |
| AC-09 | Категории | В начальном справочнике существуют не менее четырёх категорий; дубликат названия отклоняется. |
| AC-10 | База данных | `schema.sql` выполняется на пустой базе, затем `seed.sql`; внешние ключи включены, тестовые запросы выполняются без ошибок. |
| AC-11 | Интерфейс | Существуют не менее пяти согласованных экранов: вход, список, создание, карточка, редактирование; предусмотрены ошибки и подтверждение удаления. |
| AC-12 | Документация | ТЗ, диаграммы, прототип, SQL, результаты проверок и AI-журнал находятся в репозитории и соответствуют друг другу. |

## 8. Границы учебной версии

В текущем этапе проектируются требования, архитектура, интерфейс и база данных. Полноценная серверная аутентификация, отправка уведомлений, загрузка вложений и нагрузочное тестирование являются следующими этапами и не выдаются за уже реализованные функции.
