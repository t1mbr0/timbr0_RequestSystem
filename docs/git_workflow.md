# Git-workflow учебного проекта

**Разработчик:** timbr0 (`timbr0@mail.ru`). Настройки имени и e-mail выполнены локально для этого репозитория и используются только как подпись авторства коммитов.

## Выбранная модель

- `main` — основная стабильная ветка, которую можно показать преподавателю; изменения попадают в неё после проверки в `develop`.
- `develop` — рабочая ветка для отдельного изменения и проверки слияния.
- Каждый коммит отражает один законченный этап: структуру, README, ТЗ, диаграмму, архитектуру, интерфейс, базу или отчёт.
- Перед коммитом проверяются `git status` и состав изменений; секреты и локальные окружения не добавляются.

## Основные команды

| Команда | Назначение |
|---|---|
| `git --version` | Проверить установленную версию Git |
| `git init -b main` | Создать локальный репозиторий с основной веткой `main` |
| `git config user.name "timbr0"` | Задать имя автора только в текущем репозитории |
| `git config user.email "timbr0@mail.ru"` | Задать e-mail автора только в текущем репозитории |
| `git status` | Показать изменённые, добавленные и неотслеживаемые файлы |
| `git add <файл>` | Подготовить выбранные изменения к коммиту |
| `git commit -m "сообщение"` | Сохранить подготовленный снимок в истории |
| `git switch -c develop` | Создать ветку `develop` и перейти на неё |
| `git switch main` | Вернуться в основную ветку |
| `git merge develop` | Перенести историю `develop` в текущую ветку `main` |
| `git log --oneline --graph --all` | Проверить историю и слияния |
| `git branch -a` | Показать локальные и удалённые ветки |
| `git remote add origin <URL>` | Связать локальный репозиторий с GitHub |
| `git push -u origin main` | Отправить `main` и настроить отслеживание удалённой ветки |
| `git push origin develop` | Отправить ветку `develop` |

## Безопасность команд

`git merge develop` не удаляет историю, но может создать конфликт, если одна строка изменена в обеих ветках. Перед слиянием нужен чистый рабочий каталог и проверка текущей ветки. `git push -u origin main` отправляет коммиты на сервер, поэтому сначала проверяются URL удалённого репозитория и содержимое истории. Команды `reset --hard` и `push --force` в работе не используются: они могут безвозвратно удалить локальные изменения или перезаписать чужую историю.

## Фактический конфликт и его разрешение

В коммите `450338c` на ветке `main` описание `main` было изменено на «основная стабильная ветка, которую можно показать преподавателю в любой момент». В коммите `61728ec` на ветке `develop` та же строка получила другое дополнение: «изменения попадают в неё после проверки в develop». При выполнении `git merge develop` Git сообщил: `CONFLICT (content): Merge conflict in docs/git_workflow.md`.

Я открыл файл и обнаружил маркеры `<<<<<<< HEAD`, `=======` и `>>>>>>> develop`. Автоматически выбирать одну сторону было бы неправильно, поскольку оба уточнения полезны. Я вручную объединил их в одну формулировку: `main` является основной стабильной веткой, а изменения попадают в неё после проверки в `develop`. Заодно сохранил уточнение, что `develop` является рабочей веткой. Маркеры конфликта удалены, результат добавлен через `git add` и зафиксирован merge-коммитом.
